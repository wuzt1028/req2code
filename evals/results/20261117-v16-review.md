## 1. 决策简报（2/5）

### 事实

`/tmp/req2code-e2e-v16/docs/ai-coding/20261117-健康检查/_决策简报.md`（临时夹具，未随仓库提交）最终内容：

- 标题后直接是“结果一句话 / 交付物 / 关键口径 / risk 与 NFR / 验证结论 / 后续建议”；
- 没有“要解决的问题 / 2-4 个选项及影响与成本 / 不做的后果 / 需要你拍板”；
- 开头写“状态：已交付闭环”，是事后快照，不是停靠时的决策材料；
- 表头写“更新：2026-11-17 15:10”，文件 mtime 是 `14:35:40`，`_日志.md` 无 15:10 事件；
- 写“已上线可用”，但 P8 明确“本轮验收为本地运行时联调，未连接生产环境”。

### 判断

- **类型错误**：模板要求的是“停靠点的一页决策摘要”，agent 把最终交付总结写进了同一个文件；如果中途确实按决策简报用过，末态覆盖也丢失了决策历史。
- **业务可读性不足**：A1–A12、sha256、allowlist、X-Request-Id 等工程语言占主导；业务方仍然要读技术产物。
- **缺决策要素**：没有成本/工作量、选项对比、不做的后果、残余风险。
- **事实不一致**：时间戳、生产状态两处可验证矛盾。

### 建议

1. 把“决策简报”和“交付摘要”拆成两个文件：
   - `_决策简报.md`：每次停靠更新/追加，保留历史；字段固定为问题/选项/推荐/影响/成本/风险/不做的后果/需要拍板/审批引用；
   - `_交付摘要.md`（或 P8 末尾）：最终结果、验证、遗留、运行方式。
2. SKILL 明确“最终交付不得覆盖各停靠点的决策记录”；模板加“决策历史（append-only）”小节。
3. 模板强制“成本/工作量 + 置信度”，并给业务语言示例。
4. 模板加“事实校验”：时间戳用实际时间，不写未发生的“已上线”。

## 2. NFR 内容（3/5）

### 做得好的

- P5 §8 四维齐全：延迟/吞吐/容量、可用性/失败模式、可观测性、安全/隐私；
- 安全机制具体：日志字段 allowlist、请求头/query/body 不采集、`path` 去 query、`mask_ip`、`mask_tenant` 预留；
- 日志失败隔离有单测 T14；
- 发布/回滚有 sha256 基线 + 备份 + 回滚演练 + 冒烟，证据可复现；
- 回滚后旧版 `/health` 404 符合预期。

### 问题

| # | 严重度 | 问题 | 证据 |
|---|---|---|---|
| N1 | P0 | **NFR 目标零测量**：P95<10ms、M2 展示指标、吞吐/并发均无压测或基线；`duration_ms` 样本全为 0，只能说明本地单请求 | P5 §8 / P8 A1–A12 无 NFR 项 |
| N2 | P0 | **健康探针语义有缺口**：`HEAD /health`、`POST /health` 均 **501**，无 `X-Request-Id`、无日志；但 P5 §3.3 写“所有响应”都有 X-Request-Id，§3.4 写“每请求恰好 1 条” | 实测：`HEAD /health -> 501`、`POST /health -> 501`，GET 才 200 |

| N5 | P1 | **反向代理下 client_ip 失真**：`self.client_address[0]` + 不解析 XFF；若部署在反代后，日志 IP 恒为代理 IP，“脱敏与追踪”同时失真 | P5 §3.4/代码；未说明部署拓扑 |
| N6 | P2 | **失败模式覆盖不全**：`web/index.html` 缺失 500 未在 P8 验收项/测试中出现；stdout 阻塞/磁盘满、端口冲突、慢客户端、请求 ID 碰撞未讨论 | P5 §8 列了但证据未覆盖 |

### 建议

1. 高风险/中风险 P5 §8 增加“验证方式/证据”列；NFR 目标必须写“如何测、在哪测、结果”。
2. P8 增加 NFR 验收项（N1..Nn）或显式 `not-verified`，不能只列功能 A 项。
3. 健康检查明确 liveness/readiness：至少支持 HEAD；若只覆盖进程存活，就写明“不检测页面/依赖”，并让 LB 用 GET。
4. 部署拓扑（反代/XFF/仅 localhost）写进 P5 §8；`client_ip` 要么用可信代理解析，要么明确“仅记录直连地址”。
5. 证据按用例区分：截图 + stub 响应/URL/console 一起存；`_verify` 文件数量单独列。

## 3. risk 初判（3/5）

### 事实

```json
"risk": {"level": "medium", "data_change": false, "breaking_change": false, "security_sensitive": true}
```

P5 §8 的论证：`security_sensitive=true`（日志接触请求元数据）；`data_change=false`、`breaking_change=false`、3 文件、可秒级文件回滚 → 不升 high；升级触发条件已写。

### 判断

- **medium 可辩护**：没有数据/schema 变更、没有鉴权改造、改动收敛、回滚有演练；security_sensitive 判对。
- **但有三处论证缺口**：
  1. `breaking_change=false` 缺消费方分析：`/` 响应体从 25B 内联页变成 869B 文件页，新增 500 分支，语义上是**可见行为变更**；虽然路径/状态码/Content-Type 不变，但“返回内容契约”已变。应至少列消费方（浏览器/脚本/监控）并说明为何兼容。
  2. 环境口径自相矛盾：一边按“生产服务”评审（安全/NFR/回滚），一边用“仅监听 127.0.0.1、无鉴权”论证安全；P8 又承认未连生产。生产/本地两套假设不能混用。
  3. `client_ip` 在反代后失真（N5），会同时影响安全与可观测性；当前风险论证未覆盖部署拓扑。
- **升级 high 的触发条件**（reviewer 给的具体化）：公网/反代暴露、`/health` 接 LB 探针、真实租户/PII 入日志、引入日志采集组件、改动既有接口响应契约。

### 建议

1. 在 `_状态.md` 的 `risk` 里加 `reason` / `evidence` / `assumptions`（部署拓扑、消费方清单、升级触发），不要只写布尔值。
2. 给 `breaking_change` 下定义：**既有客户端可观察的响应体/头/语义变化**；有变化就要求消费方影响分析，即使路径/状态码不变。
3. risk 评分用显式矩阵：影响（数据/安全/可用性）× 可能性 × 可逆性，而不是三个布尔直接手判。
4. 生产假设必须写“当前部署形态”：localhost? 反代? 是否有 TLS/鉴权/日志采集？否则 NFR/安全结论无法成立。

## 5. 发布结论

- **作为本地 demo**：可交付。16 个单测、接口冒烟、日志脱敏、三态 UI、回滚演练都真实通过；证据主体不是编造。
- **作为“生产服务”**：**不能原样上线**。阻塞项：
  1. HEAD/LB 探针 501，`/health` 语义未定；
  2. NFR 目标零测量，P8 无 NFR 验收项；
  3. 决策简报无法支撑业务拍板；
  4. 生产/本地假设混用，反代/client_ip 未定。
- 放行条件：定探针 method 与 liveness/readiness → NFR 测量或标 `not-verified` → 决策简报改为决策型并保留历史 → 部署拓扑/日志采集/告警责任人落纸。
