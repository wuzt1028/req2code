# 产物目录、模板与交接协议

## 一、目录约定

```
{产物仓库}/docs/ai-coding/{YYYYMMDD}-{需求短名}/
├── _状态.md
├── P0-输入与仓库侦察.md
├── P1-PRD.md
├── P2b-评审确认包.md            # 可选（Phase 2 产出，用户需要正式评审物料时）
├── P3-设计说明.md
├── P3-交互原型.html
├── P4-场景与测试Case.md         # 默认必做（全栈必做）
├── P5-开发设计.md
├── P8-验收记录.md               # Phase 8
└── .verify/                     # 实测与验证证据（原型截图、联调截图等）
```

规则：

- **产物仓库**：默认需求所属主仓库（或用户指定）；前后端跨仓库时，`P0` 中记录全部仓库绝对路径，产物统一落在一处。
- **需求短名**：2-8 字，不含空格与特殊字符（如 `慢查询分析`）。
- **日期**：需求启动日，`YYYYMMDD`。
- **编号**：文件名用 `P{阶段}-` 前缀，与 Phase 号对齐（`P0/P1/P2b/P3/P4/P5/P8`）；Phase 6/7 的产出回填 `P5` 实施状态，不单独成文件。
- **历史目录兼容**：既有目录沿用旧编号（`00-/01-/02-/02b-/03-/04-/05-`），续跑历史需求时沿用原文件名，不做重命名迁移。
- **`.verify/`**：Phase 3 原型实测与 Phase 8 联调的截图/证据目录，随产物目录保留，不单独入库（由用户决定）。
- **入库**：产物是否提交到仓库由用户确认（默认随仓库惯例）；不入库时提示用户加入 `.gitignore`。
- **状态**：`_状态.md` 是续跑与诊断的唯一状态来源，每阶段结束更新（含"最后更新"日期）。
- 所有产物文件头部固定带「输入来源」区块：上游文件绝对路径 + 版本/日期（`_状态.md` 除外，它记录整体状态）。
- 下游产物引用需求编号 `Rn` 时，格式为 `[Rn]`，保持全链路可追溯。

## 二、确认状态协议

每条结论/条目必须处于且仅处于以下三态之一：

| 状态 | 含义 | 能否向下游传递 |
|---|---|---|
| `AI推断` | AI 提出，未经验证 | 不能；必须显式标注并列入待确认 |
| `用户确认` | 操作者（研发/PM）确认 | 能 |
| `客户确认` | 需求方/客户确认 | 能（最高级别） |

硬性规则：

1. 未确认项不得默认通过、不得作为下游设计依据；下游产物必须保留其 `AI推断/待客户确认` 标记。
2. PRD 整体状态为「待客户确认」时，原型/开发设计/代码必须声明该前提（如"基于待客户确认的 PRD v2 实现"）。
3. 确认记录格式：

```
| 结论/条目 | 状态 | 确认人 | 时间 | 备注 |
|---|---|---|---|---|
| R1 慢查询 TopN 列表 | 客户确认 | 张三（运维负责人） | 2026-09-15 | 评审会确认 |
```

4. 不伪造确认：没有真实确认来源时，一律标 `AI推断`。
5. **确认落盘三件套**：用户每次确认时，立即同步 ① 产物头部状态 ②「确认状态」表 ③ `_状态.md` 对应行（状态/确认人/日期）；只口头确认不落盘视为未确认。

### 编号约定（全链路）

| 前缀 | 含义 | 所在文件 |
|---|---|---|
| `R1..Rn` | 需求条目 | `P1-PRD.md` 需求清单 |
| `Q1..Qn` | 澄清问题 | `P1-PRD.md` 澄清记录 / `_状态.md` |
| `D1..Dn` | 设计决策 | `P5-开发设计.md` 决策记录 |
| `A1..An` | 验收项 | `P8-验收记录.md` |
| `B1..Bn` | Bug | `P8-验收记录.md` |

规则：编号只增不复用；废弃时保留编号并标 `(已废弃)`，禁止重排。

## 四、交接协议

1. 每个产物头部记录「输入来源」：上游文件绝对路径 + 版本/日期。
2. 下游只读上游文件，不依赖会话记忆；提示词模板中的路径占位符必须填绝对路径。
3. 引用需求条目一律带 `[Rn]`，保证 PRD → 原型页面 → 接口 → 改动点 → 验收项全链路可追溯。Rn 编号只增不复用：需求废弃时保留编号并标 `R3(已废弃)`，禁止重排或复用编号。
4. 任何阶段发现上游有误：不擅自改上游文件，先报告用户，确认后回上游阶段更新。
5. 每阶段结束更新 `_状态.md`；下游续跑只依据 `_状态.md` 与产物文件，不依赖会话记忆。
6. 上游升版后，回填所有下游产物「输入来源」的版本号。

## 五、变更回传规则

1. 需求变更 → 回 Phase 1/2 更新 `P1-PRD.md`（升版本 + 变更记录），并标注受影响的下游文件。
2. 设计变更（原型）→ 更新 `P3-*`，同步检查 `P5-开发设计.md` 中映射的原型界面与 Rn。
3. 开发设计变更 → 更新 `P5`，若代码已实施，标注受影响改动项并回 Phase 6/7 修正。
4. 所有变更在受影响文件的「变更记录」留痕；未确认的变更不得静默生效。
