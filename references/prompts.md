# 提示词模板

各阶段的可粘贴指令 payload。使用方式：按 `{占位符}` 填充上下文后，作为任务指令执行；流程定义以 [SKILL.md](../SKILL.md) 为准，本文件不另立流程。各阶段完成后更新 `{产物目录}/_状态.md`。产物文件命名用 `P{阶段}-` 前缀（见 [artifacts.md](artifacts.md)）。

通用占位符：

| 占位符 | 含义 |
|---|---|
| `{产物目录}` | 需求产物目录绝对路径，如 `/repo/docs/ai-coding/20260915-慢查询分析` |
| `{后端仓库}` / `{前端仓库}` | 仓库根目录绝对路径 |
| `{参考仓库}` | 视觉与交互的参考前端仓库绝对路径（默认同 `{前端仓库}`） |
| `{需求名}` | 需求短名 |
| `{Rn}` | 需求编号，如 R1、R2 |

---

## 1. 产品需求模板（Phase 1a-1b → P1-PRD.md）

```
我现在有个用户需求，请扮演资深产品经理，先调用 prd-writing skill 生成 PRD。skill 不可用时按下方【输出结构】自行生成。

【需求原始输入】
{需求描述，例如：目前我想在基于 skywalking 的 apm 模块中，统一设计一个慢查询分析的设计，主要想帮助研发/应用运维排查慢查询 SQL、哪些服务占用数据库资源、上线前后/关键时间点对比是否出现新的慢查询 SQL}
{调研结果文件路径 / 粘贴调研摘录（如有）}

【输出结构】
0. 需求理解复述（5 要素：背景 / 使用角色 / 场景 / 最终目的 / 需求边界），每条标注 [有证据] 或 [无证据-观点驱动]；附「待确认清单」
1. 问题背景与证据（有数据/用户引述/现象；没有就标注"无证据，观点驱动"）
2. 目标与成功指标（量化 + 反指标，如"激活率提升至 70%，且 30 日留存不低于 45%"）
3. 目标用户（具体，不宽泛，写清"谁 + 什么情境 + 为什么需要"）
4. 使用角色、权限与触点
5. 核心场景与用户旅程（3-5 个，标注主/次）
6. 需求清单（按 P0/P1/P2 拆分，P0 限 3-5 条，每条一句话，编号 R1..Rn）
7. 明确不做（Out of Scope，注明原因）
8. 边界与约束（技术/合规/时间）

【流程约定】
- 第一轮：先只输出第 0 节「需求理解复述 + 待确认清单」，等我确认或修正后再继续（禁止跳过）
- 第二轮：基于确认后的理解生成第 1-8 节 PRD 初稿（v1），停靠等我确认
- 澄清（Phase 2）按模板 2 单独执行，不在本模板内进行

【约束】
- 每条结论标注证据状态；不确定项进待确认清单，禁止静默假设
- 需求编号 R1..Rn 必须可被后续原型/接口/改动点/验收引用
- 不替客户拍板：我无法回答的记入「待客户确认」
- 输出写入 {产物目录}/P1-PRD.md
```

## 2. 需求澄清模板（Phase 2，grill 模式）

```
请对 {产物目录}/P1-PRD.md 启动 grill 模式（优先调用 grilling skill；不可用时按下述清单逐条追问）。

【执行方式】
- grilling 可用：按其轮次机制执行——一轮问完当前 frontier，等我回答后再进入下一轮
- grilling 不可用：按下述 6 个维度逐条追问，一次最多问 3 个问题
- 两种方式共同要求：每个问题给出 2-4 个选项与推荐答案，不允许开放式提问

【追问维度】
1. 目标可量化吗？（指标有没有数字？反指标是什么？）
2. 场景真实吗？（谁在什么情境下用？频率多高？现在怎么解决的？）
3. 边界清晰吗？（明确不做的是什么？哪些是 P0 之外的？）
4. 优先级对吗？（P0 超过 5 条吗？砍掉哪条需求仍然可用？）
5. 约束漏了吗？（技术/合规/时间/依赖方约束？）
6. 证据充分吗？（哪些是无证据观点驱动？需要向客户确认什么？）

【流程约定】
- 澄清问题编号 Q1..Qn（只增不复用），我的回答整理进 PRD v2；我回答不了的记入「待客户确认」
- 全部澄清完成后：输出修订后的 PRD v2 + 评审要点（给客户/产品/UI/测试的确认要点与待确认问题清单），等我确认

【约束】
- 不替我做决定；我只说"你决定"时，给出推荐选项及理由，并标注为 AI推断
```

## 3. 交互设计模板（Phase 3 → P3-设计说明.md + P3-交互原型.html）

```
上面已经做了需求的 PRD（{产物目录}/P1-PRD.md），请扮演资深前端设计工程师，制作可交互的 HTML 原型，视觉与交互严格复刻参考仓库。

【输入】
- PRD：{产物目录}/P1-PRD.md
- 参考前端仓库样式和交互：{参考仓库绝对路径 / 截图 / URL}
- 目标前端仓库（实现落地处）：{前端仓库绝对路径}

【流程约定】
- 第一轮开始前：用一句话声明你选定的参考源（默认 {参考仓库}），等我确认或改指后再做设计说明——不得自动扫描后静默选定
- 第一轮：先输出设计说明——信息架构、页面清单（映射 Rn）、组件清单、交互状态矩阵（默认/加载/空态/错误/禁用/权限不足）、响应式断点、风格来源与 token 提取映射表（色板/字号/间距/圆角/组件与交互模式），等我确认
- 第二轮：确认后实现单文件 HTML（内联 CSS/JS，无外部依赖，双击可运行）
- 第三轮：用浏览器实测全部交互状态，截图存入 {产物目录}/.verify/，记录控制台错误；用 anti-ui-slop 的 finish gate（或内置 rubric，标注 Fallback）自审并整改：是否通用模板感、交互状态是否完整、响应式是否到位、可访问性（对比度/键盘/焦点）是否达标；附一致性自检（与参考源一致项 / 有意偏离项及原因）

【实现要求】
1. 覆盖 PRD 全部场景的页面与流转，页面清单逐一映射需求编号 Rn
2. 复刻参考仓库的视觉语言，不引入仓库外的新风格
3. 覆盖全部交互状态：加载/空态/错误态/禁用态（权限不足态如有）
4. 结构与 class 命名清晰，便于后续交接给前端工程师按组件落地
5. 设计说明写入 {产物目录}/P3-设计说明.md，原型写入 {产物目录}/P3-交互原型.html

【约束】
- 无参考源时先走 anti-ui-slop / frontend-design 方向设定，经我确认后再实现，禁止凭空发挥
- 我要求精准修改时，我会指定文字或元素的 class/id
```

## 4. 开发设计模板（Phase 5 → P5-开发设计.md）

```
我现在要基于需求设计做对应的开发设计，请扮演资深后端架构师，根据给出的需求设计、交互设计，输出开发设计文档，这个开发设计要能满足给到负责对应前端开发的 AI 完成预期的前端代码。

【输入】
- 需求设计（绝对路径）：{产物目录}/P1-PRD.md
- 交互 demo 设计（绝对路径）：{产物目录}/P3-交互原型.html（设计说明：{产物目录}/P3-设计说明.md）
- 后端仓库：{后端仓库绝对路径}
- 前端仓库：{前端仓库绝对路径}
- 仓库侦察记录：{产物目录}/P0-输入与仓库侦察.md

【设计】基于摘要与需求交接包输出《开发设计文档》，固定结构：
1. 业务流程图（mermaid flowchart + sequenceDiagram，标注本次改动点）
2. 数据结构变化（新增/修改/删除表与字段、约束、索引、迁移方案、存量数据处理）
3. 接口设计（新增/修改：方法、路径、请求/响应字段表、错误码表、鉴权、幂等性；破坏性变更必须标注"不兼容"）
4. 后端改动代码结构（新增/修改/删除文件清单、模块边界、复用现有组件、每个改动点的影响面与风险）
   - 每个新增文件必须回答"为什么不能复用现有 X"；存在可复用组件而选择新建需写明理由
5. 前端改动点（页面/组件/接口调用/状态管理，逐一映射到 HTML 原型中的对应界面与需求编号 Rn），能让前端开发 AI 直接读取分析后完成代码编写
6. 关键决策摘要（800 字内，列最重要的 3-5 个决策及理由；含「最简方案 vs 推荐方案」取舍）

【约束】
- 参考后端仓库代码，识别技术栈与版本、分层与目录结构、命名/异常/鉴权/接口风格约定、数据库访问方式、多租户与数据可见性边界、已有相似功能可复用点。一切设计遵循仓库现有约定，不引入新框架、新风格
- **最简方案优先**：默认扩展现有实体/接口/组件；每张新增表、每个新增接口/任务/依赖逐项说明"为什么不能复用或不新增"，禁止未经对比直接引入新存储/新任务/新组件
- **可行性结论必须有证据**：凡"做不到/有代价/不支持"的结论，附语法或机制级证据（代码位置、PromQL/框架语义）；证据不足列为待验证项，不得直接砍需求
- 决策编号 D1..Dn（结论/确认状态/影响），维护在「决策记录」表
- 向后兼容优先；设计必须可被仓库内实际代码验证，禁止凭空假设
- 设计文档要能被"另一个 AI"直接拿去写代码，无需再问需求
- 输出写入 {产物目录}/P5-开发设计.md；我确认后才允许进入编码
```

## 5. 后端实施模板（Phase 6）

```
基于 {产物目录}/P5-开发设计.md 的「后端改动代码结构」在后端仓库 {后端仓库} 内实施：

进入前核对：P1-PRD.md 状态=已确认 且 P5-开发设计.md 状态=已确认 且 _状态.md 对应行一致；不一致先修复再实施。

1. 严格遵循当前工程代码风格、分层结构与编码规范
2. 复用优先：先检索仓库内相似实现（同类 Service/DAO/工具类/拦截器），优先复用或扩展现有组件，不重复实现
3. 按改动清单逐项实施，每完成一批报告：改了哪些文件、如何验证、有无偏离设计
4. 新增依赖/工具必须先列出并等我确认，不得自行引入
5. 接口实现严格按设计文档契约（路径/字段/错误码/鉴权/幂等），不自行调整
6. 发现设计不可行时停止实施，回写设计中问题点，等设计更新后再继续

【完成后】回填 {产物目录}/P5-开发设计.md 的实施状态（文件清单勾选 + 验证结果）
```
